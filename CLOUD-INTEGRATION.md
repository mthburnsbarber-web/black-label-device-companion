# Cloudflare device relay contract

**Integration update:** Council's existing Worker source in task-2 now implements the `/health`, `/frames`, `/enroll`, and owner pairing routes on a separate device hostname. That is the intended single backend for the dashboard and this companion. The `cloud/` Worker in this repository is an earlier standalone reference and must not be deployed alongside Council. `native/council_enrollment.js` implements the device's enrollment request against Council's contract, but no invitation, service token, identity fingerprint, pair key, or actual device has been provisioned. Council's approval and directional pair routes remain owner actions. The native CLI does not invoke enrollment yet; its `--start` mode requires completed provisioning.

The deployed Council dashboard currently has no device relay (`/api/clipboard/validate` returns 501). This repository now includes a **separate, undeployed** [Cloudflare relay Worker](cloud/relay_worker.js), [D1 schema](cloud/schema.sql), and [configuration template](cloud/wrangler.example.jsonc). It is fail-closed until each device has a dedicated path-scoped Cloudflare Access service application with a distinct audience and a service-token policy, a paired-device registry, and a dedicated D1 binding. Cloudflare documents the `CF-Access-Client-Id` and `CF-Access-Client-Secret` [service token headers](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/) for automated clients and recommends validating the [Access JWT assertion](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/) at the Worker. `HttpRelayClient` accepts externally supplied `{clientId,clientSecret}` and sends those headers. The existing owner-email browser JWT check is not a substitute for per-device identity.

## Wire routes

- `GET /devices/{deviceId}/health`: requires a valid device-specific Access application JWT. Returns `{ok:true}`.
- `POST /devices/{deviceId}/frames`: device identity comes from the path **and its verified, unique Access audience**, never the untrusted `x-device-id` header alone. Body `{to,payload,expiresAt}`. `payload` is an opaque AEAD frame. The Worker enforces paired destination, expiry no more than 30 seconds, and size limits. Per-device rate limits and quota controls still need Cloudflare policy configuration before deployment. Return `{seq}` on enqueue.
- `GET /devices/{deviceId}/frames?after=N`: returns at most 100 `{seq,from,payload,expiresAt}` entries for the authenticated recipient only. `from` is set by the relay from verified source identity. Expired frames are not returned. D1 preserves cursor order across reconnects.

Only the paired endpoint can decrypt `payload`. The reference `PairwiseAeadCodec` uses AES-256-GCM with a fresh nonce per frame and authenticates source and target IDs in associated data. Keys must be unique per pair and provisioned through an approved, revocable enrollment flow into native credential stores. A real deployment needs key rotation and replay review before handling sensitive clipboard data. The loopback test uses fixed **test-only** keys and tokens; they are never suitable for a live relay.

The Worker stores encrypted frames temporarily in a dedicated D1 table and deletes expired rows on requests and an hourly scheduled cleanup. D1 may retain backups beyond the application TTL, so retention and data-location implications need review before real clipboard data is sent. The owner dashboard should expose **status metadata only**: device connected/last-seen, paused, capability, transfer ID, attempts, and `received`/`applied`/`verified` state. It must not log or add plaintext, ciphertext, short-content hashes, device service tokens, or pair keys to room events. Cloud queue success is not proof of recipient write. A target must issue authenticated `verified` only after its native clipboard readback matches the expected revision, byte length, and SHA-256.

## Activation gates

1. Complete owner-approved device enrollment and a separate Cloudflare Access **Service Auth** policy for each `/devices/{id}/*` path, with a unique audience per device. Verify that one device's token cannot access another device's path, and verify revocation.
2. Bind the relay to a separately approved hostname or route without weakening the existing Council browser Access rule. Apply rate limits and a D1 cleanup schedule before enabling any device.
3. Provide pair keys through an approved native credential-store flow. Never put them in this repository, browser storage, a URL, or dashboard D1 room records.
4. Verify one actual Mac-to-Mac pair with explicit clipboard permission, short/multiline/Unicode/64 KiB values, disconnect/reconnect, stale revision, permission denial, and recipient readback. Then assess Windows and Linux adapters separately.

The Worker routing and fail-closed behavior have local tests with an injected frame store. Access JWT signature, issuer, audience, and expiry checks use ephemeral test keys. The real D1 binding, Access service policy routing, and live retention have **not** been integration tested. No Cloudflare resource, service token, pair key, OS permission, or real clipboard has been created or accessed by this repository's tests.
